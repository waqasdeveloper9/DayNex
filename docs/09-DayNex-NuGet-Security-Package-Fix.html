Fixing the vulnerable Pkcs dependency

A focused package update across Identity, Holiday and UserInfo services.

1 · What the warning meant

Visual Studio reported System.Security.Cryptography.Pkcs 9.0.11 as vulnerable. It was transitive: our projects did not directly request it, but the SQL Server dependency did.

Microsoft.EntityFrameworkCore.SqlServer 10.0.12
  → Microsoft.Data.SqlClient 6.1.6
    → System.Security.Cryptography.Pkcs 9.0.11

Microsoft's advisories identify denial-of-service vulnerabilities in CMS/PKCS processing. The warning identifies an affected dependency; it is not evidence that DayNex has been attacked or that its normal API routes exercise the vulnerable operations.

High-severity advisory · Moderate-severity advisory. Both list 10.0.13 as a patched release in the .NET 10 package line.

2 · The targeted fix

DayNex already uses Central Package Management. The patched version is defined once in Directory.Packages.props:

<PackageVersion Include="System.Security.Cryptography.Pkcs" Version="10.0.13" />

Each of the three affected Infrastructure projects explicitly references that centrally versioned package:

<PackageReference Include="System.Security.Cryptography.Pkcs" />

This overrides the lower transitive request and flows through to the API projects and tests. A central PackageVersion alone does not override transitive dependencies when transitive pinning is not enabled. We used targeted references instead of enabling a broader dependency policy.

The version matches our net10.0 applications. We did not suppress NuGet audit warnings or update unrelated packages. No database migration is needed.

3 · Reproduce the checks

Run these from the backend repository root:

dotnet nuget why DayNex.sln System.Security.Cryptography.Pkcs

dotnet restore DayNex.sln --force-evaluate

dotnet test tests/DayNex.Tests/DayNex.Tests.csproj --no-restore -m:1

dotnet list DayNex.sln package --vulnerable --include-transitive --no-restore

Verified: restored graphs and all three API runtime dependency manifests resolve Pkcs 10.0.13. The dependency build and 109 tests passed; 2 optional SQL integration tests were skipped. NuGet audit found no known vulnerable packages across all 17 solution projects.

Vulnerability auditing checks published advisories known to the configured feed. A clean report is not a general guarantee that an application has no security defects.

4 · Visual Studio and deployment

An initial parallel solution build encountered missing generated shared assemblies. Rebuilding the test project and its service dependencies serially succeeded; no source or database change was required for that build-artifact issue.

  1. Reload changed projects if Visual Studio prompts.
  2. Open Manage NuGet Packages for Solution and choose nuget.org in the Package source dropdown. The screenshot had Microsoft Visual Studio Offline Packages selected; nuget.org was already enabled in the machine configuration.
  3. Run Restore NuGet Packages and refresh the Installed tab if its display is stale.
  4. Restart running services so they load newly built assemblies.
  5. Rebuild and redeploy container images before expecting deployed containers to contain this fix. Updating source does not modify existing images.

This package fix does not update your globally installed .NET SDK, Visual Studio installation or already-published runtime images. Those have separate patch lifecycles.

5 · Interview questions

What is a transitive dependency?

A package required by another dependency. It can affect your application even when it is absent from your own PackageReference list.

Why add an explicit reference?

It selects the patched version for the affected dependency graph. The version remains central so the three services cannot silently drift to different versions.

Why not suppress NU1902/NU1903?

Suppression only hides the report. Resolving an unaffected package version addresses this known package issue.

How do you validate a dependency patch?

Trace the original dependency, check the vendor advisory and compatible fixed version, restore, inspect resolved assets, build, run relevant existing tests and re-audit transitive packages.

Does a clean vulnerability scan mean production is fixed?

No. The source dependency graph may be fixed while old running processes or images retain the previous assemblies. Rebuild and restart or redeploy the affected application.
