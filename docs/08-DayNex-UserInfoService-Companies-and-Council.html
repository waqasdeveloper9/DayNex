What is implemented

VehicleService has become DayNex.UserInfoService. The service owns vehicles, company references, company-profile snapshots and postcode/council selections. Identity remains responsible for authentication-linked profiles and onboarding preferences. Existing API paths and ports are retained.

Company profile lookup uses the public Companies House profile API. It does not submit filings, retrieve private accounting records, verify directorship, or retrieve insurance policy details. The existing scheduled job still refreshes vehicles, not companies.

Final verification: 109 backend tests passed; 2 optional SQL integration tests skipped. Android unit tests and debug APK assembly passed. All 28 project references and Docker Compose configuration validate. The real .NET council client returned Bradford after the restricted redirect fix. Companies House live verification remains pending a REST API key. Docker Desktop is stopped, so the renamed container image has not been rebuilt. The previously reported Pkcs package warnings were subsequently fixed; see guide 09 for the patched dependency and verification.

2 · Request flow

Controllers adapt HTTP requests. Application services coordinate work through interfaces. Infrastructure handles HTTP authentication, provider model mapping and EF transactions. Providers never receive the customer's DayNex bearer token.

3 · Persistence model

Company snapshots are user-reference scoped initially. A future shared company cache can reduce calls when many users follow the same company. Public company data does not establish the user's authority over it.

Core fields are typed for queries and dashboard cards. Raw JSON preserves optional provider fields without exposing all of them in customer DTOs. Missing dates remain null, never invented deadlines. Modern accounts.next_accounts.due_on takes precedence over the legacy fallback.

4 · Companies House credentials and Postman

  1. Open the Companies House developer guide and sign in/register.
  2. Open your developer applications and create a DayNex application for the appropriate environment.
  3. Create a REST API key following application setup. Configure any restrictions to match your actual calling environment.
  4. In Postman create the request below. Choose Authorization → Basic Auth. Username is the API key; password is empty. Use no request body.
  5. For the backend, run the secret helper below. Do not paste the key into appsettings, Git, screenshots or HTML.

Username: YOUR_REST_API_KEY

5 · Optional onboarding and API contracts

Method / pathBehaviour
GET /api/assets/meSaved vehicles, companies and optional location/council. No provider requests.
POST /api/assets/me/companiesSave reference first; enrich once when no lookup has been attempted.
GET /api/assets/me/companies/{id}Owner-scoped saved profile.
POST /api/assets/me/companies/{id}/refreshExplicit retry, with a five-minute per-reference cooldown.
PUT /api/assets/me/locationNormalize and save postcode, resolve council, or clear with an empty string.
GET /api/assets/me/locationRead the current saved location.
POST /api/assets/me/onboardingOptional batch facade; validates all supplied references first. Maximum 20 of each type.
POST /api/assets/me/onboarding
Authorization: Bearer YOUR_DAYNEX_ACCESS_TOKEN
Content-Type: application/json

{
  "postcode": "BD15 7QW",
  "vehicleRegistrations": ["AB12CDE"],
  "companyNumbers": ["00000006"]
}

These are illustrative references, not a claim of ownership. Null/omitted postcode means leave the selection unchanged; an empty string clears it. An empty onboarding body creates no provider requests.

The Android repository uses small per-reference calls and then PUT location before saving Identity onboarding preferences. This avoids one enormous batch request. Previously saved references are idempotent; companies entered again can enrich legacy references. If a provider fails, saved input remains and the dashboard displays lookup status. Users can skip and add details later. For large imports use small batches; a future durable background queue is preferable to increasing mobile HTTP timeouts.

Postcode ownership: UserInfo's saved postcode is the source for council matching. Identity currently retains its existing postcode preference for compatibility. The Android save flow updates both; clients that call only the Identity preference endpoint must also call PUT location. This is not a distributed transaction, so an interrupted save should be retried.

6 · Edge cases and failure behaviour

  • Whitespace and casing normalize; company numbers remain strings to preserve leading zeros.
  • Duplicate references return the same saved association. Per-user limits remain enforced transactionally.
  • A changed postcode clears the old council before network access. Clearing the postcode removes the council association.
  • Revision plus attempt guards stop a slow response restoring an old council, including A → B → A changes.
  • 401/403, 404, 429, timeouts and malformed provider payloads become safe status values. Request cancellation is propagated.
  • A failed company refresh preserves the last successful profile and retrieval time. The frontend marks saved data as stale when the latest lookup failed.
  • Deleting a company cascades snapshot children. Late responses cannot recreate deleted references.
  • Unknown optional company fields stay in the raw snapshot. Company-number mismatch is rejected.
  • Named clients have bounded response size, timeouts, limited jittered retries, credential-header redaction and no automatic redirects. Council lookup permits one validated HTTPS redirect to the same GOV.UK council API path.
  • Future council-specific jobs must bind to the postcode revision. The revision is an extension point; no downstream council jobs are implemented yet.

9 · Interview questions and explanations

Why separate identity from user information?

Authentication establishes the caller; UserInfo owns feature data and provider snapshots. An Identity user ID is a logical reference, not a cross-database foreign key.

Why keep typed columns and JSON?

Typed deadlines support indexed queries and stable contracts. The full snapshot preserves optional provider fields for future mapping. We return deliberately selected DTOs rather than exposing raw provider data everywhere.

Why is a postcode revision necessary?

HTTP responses can arrive out of order. A revision identifies the exact selection that started the request; the store rejects an older revision even if the user later enters the same postcode again.

Why preserve a successful snapshot after failure?

Temporary provider failure should not erase useful saved information. Status and retrieval timestamps make freshness explicit.

Why not forward the customer's token to Companies House?

It has the wrong issuer/audience and grants no Companies House permission. Public reads use our developer API key; filing would require a separate authorised integration.

Is signup enrichment atomic across services?

No. There is no distributed transaction across Identity, UserInfo and government providers. Save input first, make repeated writes safe and expose per-provider results so retries can repair partial completion.

Why not rename the SQL database and secret store?

The application boundary changed, not the existing data. Keeping stable persistence identifiers reduces operational risk and preserves credentials. We document these compatibility identifiers explicitly.

How would you add council-specific jobs later?

Read the current council and revision, associate scheduled work with that revision, and invalidate or ignore obsolete work when the selection changes. Add an outbox if reliable cross-service events become necessary.
