06 · DVSA MOT integration

Implementation guide · 11 October 2026 · .NET 10

What has been implemented

VehicleService saves the customer's registration first, calls DVLA VES, and then calls DVSA MOT history. Both providers use the shared HTTP abstraction. Each provider has its own status and saved snapshot. A provider outage does not remove the customer's registration or the last successful MOT history.

DVLA VES is not an insurance API. It provides vehicle, tax and MOT information. Insurance expiry requires a separate authorized provider; no insurance integration has been invented.

MOT remains disabled by default until your newly issued DVSA credentials are available. The code has been tested using fake HTTP responses and SQLite. Live DVSA access has not been verified.

1. Understand the two Entra tokens

TokenWho obtains it?Purpose
DayNex customer access tokenAndroid or Postman, through the DayNex External ID tenant and Google loginAccess to the customer's DayNex API resources. The gateway and service validate it.
DVSA application access tokenVehicleService, using DVSA-issued client credentialsCall the DVSA provider. This token never comes from the mobile app.

The DVSA token URL contains the tenant supplied by DVSA. Do not replace it with your DayNex Users tenant. The provider client ID and API key also come from DVSA, rather than the DayNex Postman app registration.

2. Configure paths and credentials

Open src/Services/DayNex.VehicleService/DayNex.VehicleService.API/appsettings.json. Public endpoints and the scope are configuration. Secrets are absent from the tracked file.

"Mot": {
  "Enabled": false,
  "BaseUrl": "https://history.mot.api.gov.uk/",
  "RegistrationPath": "v1/trade/vehicles/registration/",
  "TokenEndpoint": "",
  "ClientId": "",
  "Scope": "https://tapi.dvsa.gov.uk/.default"
}
SettingWhere to obtain it
Mot:TokenEndpointAccess-token URL in your new DVSA credential email
Mot:ClientIdDVSA application identifier from that email
Mot:ClientSecretNew DVSA client secret value; enter it privately
Mot:ApiKeyNew MOT history API subscription key

From the backend root, run:

.	oolsSet-VehicleSecrets.ps1 -Mot

This stores the values in DayNex-VehicleService-Development User Secrets and enables MOT. It preserves other secrets. Restart the API after changing settings. In hosting, use secret environment variables Mot__ClientSecret and Mot__ApiKey. Never embed them in a Dockerfile or Android app.

Token requests use POST form encoding: grant_type=client_credentials, client ID, client secret, and scope. MOT requests use GET plus Authorization: Bearer <DVSA token> and X-API-Key. TLS certificate validation remains enabled; redirects are disabled to avoid forwarding credentials to other hosts. The existing DVLA proxy setting does not automatically apply to the DVSA clients.

4. Database design

TableMeaning
UserVehiclesUser ID, normalized registration, independent DVLA/MOT statuses and attempt/retrieval times.
VehicleMotHistoriesOne current provider snapshot per saved user vehicle, with make/model, dates and outstanding recall status.
VehicleMotTestsMany test records belonging to a snapshot. Test numbers are nullable and not assumed unique.
VehicleMotDefectsMany defects per test: text, type and nullable dangerous flag.

These are shared tables with foreign keys, not a new SQL table for every registration. UserId is a logical reference to IdentityService; there is no cross-database foreign key. Snapshot replacement is transactional. A failed lookup preserves the previous good snapshot. Deleting a saved vehicle cascades to tests and defects, and stale in-flight updates cannot recreate the deleted row.

Dates match the current API: ISO dates and timestamps, nullable CVS completion dates, string odometer readings and engine size. The deprecated legacy array/rfrAndComments format is rejected.

5. Read MOT through DayNex

  1. Generate the customer token through the existing Google login flow.
  2. Call GET /api/identity/me to provision/load the customer profile.
  3. Call POST /api/assets/me/vehicles with {"registrationNumber":"YOURPLATE"}.
  4. Save the vehicle ID returned by DayNex.
  5. Call GET /api/assets/me/vehicles/{id}/mot?page=1&pageSize=20 through the gateway with that same customer access token.
  6. Read the returned MOT status as well as HTTP status. Available means provider data was stored; NotConfigured means the provider is disabled.
  7. For a manual refresh, call POST /api/assets/me/vehicles/{id}/refresh after the five-minute cooldown.

Page size is limited to 50 tests. Another customer's vehicle returns 404. Registrations and provider secrets are not included in job reports. The updated Postman collection includes a MOT history request.

6. Reliability and practical limits

A singleton token provider caches tokens according to expires_in, refreshing early. A semaphore prevents concurrent requests from generating many tokens at once. Provider timeouts, limited retries with jitter and circuit breaking bound failures. MOT requests are paced at four requests per second per process, including retries. Multiple replicas would require a shared provider-wide rate budget.

StatusMeaning
NotConfiguredIntegration disabled; no external call
ProviderAccessDeniedProvider credentials/permissions rejected; check new DVSA details

AADSTS700016 indicates an application was not found in the specified tenant; it does not prove an expired secret. A provider 403 does not prove a geographical restriction. Use the provider error and official support to establish the cause.

Interview questions and explained answers

Why does the backend need a second token when the user already logged in?

The user token authorizes access to DayNex. DVSA trusts a separately registered application and issues its own token for that resource. Sending a DayNex token to DVSA crosses the wrong audience boundary.

Why not call the provider from the Android app?

Provider credentials would be extractable from the APK. The backend protects them, applies ownership and quotas, and presents a stable contract to mobile clients.

Why keep an old snapshot when refresh fails?

It allows the dashboard to remain useful during outages. The current attempt status and retrieved timestamp make staleness visible without presenting failed refreshes as fresh data.

Why use a transaction around snapshot replacement?

A reader must not see a new history row with only half of its tests. Deleting the old snapshot and inserting the complete new graph commit together, or roll back together.

How do you prevent token request storms?

Cache the provider token with its expiry and use single-flight synchronization while acquiring a replacement. Waiting callers then reuse the newly cached token.

Does retrying make a service reliable by itself?

No. Retries must be limited and safe for the operation, with timeouts, jitter, rate limits and circuit breaking. Credential errors are configuration problems, not an instruction to retry forever.
