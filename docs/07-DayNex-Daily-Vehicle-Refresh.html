1. Why this approach for our free-host practice

A scheduler running inside a sleeping backend cannot reliably wake itself. GitHub Actions runs outside the host and makes an HTTPS request. It is a practical learning/demo option, with best-effort scheduling and account usage limits. This does not guarantee a free database bill or a production SLA. A host may still time out or refuse to wake through HTTP.

OptionWhen it fits
GitHub ActionsSmall demo deployment that may sleep; scheduled runs and visible reports
Hangfire / Quartz / cronAn always-running host; more control over scheduling and retries
Queue and dedicated workersLarger workloads, independent scaling, shorter trigger requests and durable per-item retries

We have not added Azure Service Bus or a permanently running background thread. Replacing GitHub Actions does not require changing the DVSA API implementation.

3. Security boundaries

Customer Google/Entra tokens cannot trigger this all-user job. The endpoint requires the separate X-DayNex-Job-Key header. The service compares hashes in constant time. Conversely, the job key cannot access customer profile or asset endpoints. Store a random key of at least 32 characters as a hosting secret and GitHub secret; never place it in Android, source control, URLs or workflow output.

The scheduled endpoint is called directly on VehicleService over HTTPS. It is intentionally not routed through the current customer gateway: the gateway enforces customer Entra scopes globally. Opening a gateway bypass is not necessary. If future hosting exposes only the gateway, design a separate machine authorization policy before adding that route.

4. Configure local testing

  1. Make sure the Vehicle database migrations are applied.
  2. Run . oolsSet-VehicleSecrets.ps1 -RefreshJob from the backend root. Enter a newly generated random job key privately. This enables only the job setting.
  3. Configure DVLA and MOT provider credentials using the existing helper switches. Disabled providers produce NotConfigured and the batch reports failure, rather than pretending fresh data exists.
  4. Restart VehicleService. For containers, use . oolsStart-LocalContainers.ps1 -Vehicle -Build. The starter passes the saved job settings to the container.
  5. In Postman, use POST and the direct VehicleService address plus /internal/jobs/vehicles/refresh. Use No Auth and add the job header privately.
  6. With containers, the local URL is http://localhost:18083/internal/jobs/vehicles/refresh. HTTP is for local loopback development only; hosted calls require HTTPS.
  7. Expect 401 with no key, a wrong key or only a customer token. A correct key returns a batch report. Concurrent callers receive 409 while another batch owns the lease.

5. Configure hosted VehicleService

  1. Deploy the new image with the MOT and scheduling migrations applied through a separate migration step.
  2. Keep VehicleRefresh__Enabled=false until the providers and database work.
  3. Add the secret environment variable VehicleRefresh__ApiKey.
  4. Set VehicleRefresh__Enabled=true and keep batch size 1 for initial testing.
  5. Verify that the direct HTTPS job endpoint is reachable. Avoid hosts whose request timeout is shorter than provider calls; this implementation can spend up to approximately 70 seconds per vehicle in the worst case, plus database and scheduling overhead.

Batch size is validated between 1 and 3; the endpoint imposes a four-minute execution deadline. A hosting proxy can terminate the request sooner. For a host with a strict short timeout, use durable queue/worker execution instead of increasing request timeouts blindly.

6. Configure GitHub, step by step

  1. After reviewing the code, place the workflow on the repository default branch. Scheduled events run from that branch.
  2. Open the repository on GitHub → Settings → Secrets and variables → Actions.
  3. Under Secrets, click New repository secret. Name it VEHICLE_REFRESH_KEY; paste the same random key stored in hosting.
  4. Under Variables, click New repository variable. Name it VEHICLE_REFRESH_URL; enter the full direct HTTPS URL, including the configured job path.
  5. Add variable VEHICLE_REFRESH_ENABLED with value true. Leaving it unset keeps the workflow job disabled.
  6. Open Actions → Vehicle daily refresh → Run workflow for the first manual test.
  7. Open the run and read the Summary. It shows batches, processed, failed, skipped and whether the queue drained.
  8. Only after a successful manual run, leave the enable variable true for daily scheduling.

The schedule is 02:17 UTC / 07:17 Pakistan time. GitHub can delay or drop scheduled runs during load, and inactive public repositories can have scheduling disabled. This is not a guaranteed appointment time.

The workflow has no repository write permissions, checks HTTPS, blocks redirects to protect the key, and retries only selected transport/status failures. It performs at most 100 batches and runs at most 45 minutes. If the cap is reached with more work remaining, the run fails visibly rather than claiming completion.

7. Completion alerts

  1. Use the workflow Summary for the completion report.
  2. In GitHub personal Settings → Notifications, configure Actions notifications and email/web delivery as desired. Enable notifications for all runs if you want successful completion alerts too; failure-only settings will not alert on success.
  3. Inspect failed counts even when the API itself returned HTTP 200. The workflow exits unsuccessfully when provider failures occurred or the work was not drained.

No SMTP credentials or notification webhook have been configured, and no email has been sent by this code. GitHub notification delivery depends on your account preferences. A future commercial notification service can consume job completion events.

8. Progress, concurrency and recovery

VehicleRefreshJobState contains one seeded row holding a unique lease token, lease expiry and the last completed batch counts. Acquiring it uses an atomic SQL update. Two running hosts cannot acquire an unexpired lease simultaneously. Completion checks the token, so an old worker cannot release a newer worker's lease.

UserVehicles.ScheduledAttemptUtcTicks records the last scheduled attempt. Due selection uses the UTC calendar day rather than a rolling 24-hour interval, preventing a few seconds of schedule drift from skipping the next day's run. Selection and processing are bounded and sequential because a scoped EF context is not thread-safe.

An attempt marker is written before the external calls. This avoids repeated failing vehicles creating an endless loop. A failed or interrupted marked vehicle is tried on the next UTC day; this is attempt-based daily freshness, not guaranteed daily success or exactly-once delivery. Manual per-user refresh remains available after its cooldown. The ten-minute lease allows crash recovery, and provider retries handle transient failures during an attempt. Last good snapshots remain visible.

The table stores the last batch report, not a full historical audit. GitHub retains individual workflow reports under its retention policy. For thousands of vehicles, add durable per-vehicle work items, provider-wide distributed rate budgets and independently scalable workers; the small-batch demo limits are explicit.

Interview questions and explained answers

How can you replace GitHub Actions later?

Keep the application refresh service independent of the scheduler. An external scheduler calls the protected endpoint; an in-process scheduler resolves VehicleRefreshJob in a fresh dependency-injection scope and invokes it directly. Provider integration and persistence remain unchanged.

Why is a SQL lease better than an in-memory lock?

An in-memory lock coordinates only one process and disappears on restart. SQL coordinates replicas against the same persisted state. Expiry recovers abandoned work and a token fences stale completion.

Is the daily job exactly once?

No. HTTP acknowledgements can be lost and processes can crash. We use idempotent snapshot replacement, bounded retries and durable attempt markers, and state the remaining failure window explicitly.

Why not load all vehicles at once?

That grows memory use and request duration, makes restart recovery expensive and risks provider limits. Bounded reads and batches keep the failure scope small and let the caller detect unfinished work.

Why not use the user's Google token for a cron job?

A scheduled all-user operation is a machine identity with different privileges and lifecycle. User tokens expire and must not be stored as a privileged automation credential.

What would you change for production scale?

Persist per-vehicle work items and retry state, publish work to a durable queue, run dedicated workers, enforce provider-wide quotas, keep an audit trail and monitor freshness against an explicit service objective. The current application use cases can be reused.

Can free scheduling guarantee zero Azure cost?

No. Scheduling and database usage are separate meters. Configure the SQL free allowance behavior and monitor it. Do not describe a free runner as a billing cap for all dependencies.
